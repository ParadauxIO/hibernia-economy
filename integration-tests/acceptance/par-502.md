## Defects demonstrated and fixed

- A stale derived-group reconciliation could delete a member published by a newer
  binding. `DerivedGroupMapperIT.staleBindingCannotRemoveMembershipPublishedByTheCurrentBinding`
  failed before the fix and passed afterward. Removal now requires the still-current
  source and binary-equal selector, matching the publication fence. This does not
  serialize two publishers using the same selector.
- A rejected first Vault withdrawal created a SYSTEM wallet inside a transaction,
  cached its ID, then rolled back that wallet. A funded withdrawal afterward failed
  with `Account not found`. `LedgerServiceTransferIT.rejectedFirstVaultWithdrawalDoesNotPoisonSubsequentSettlement`
  reproduced this before the fix. SYSTEM resolution now uses the database instead
  of publishing an uncommitted ID into a process-wide cache. This adds an indexed
  lookup to Vault settlements; read-only balance calls are unaffected. The full
  ledger-transfer suite and root build pass.

The red XML is retained locally in `.context/par-502/stale-binding-before.xml`
and `.context/par-502/vault-rollback-before.xml`. The live Vault case additionally
injects a failed debit, checks unchanged balance/posting count, then proves recovery.

## Added live evidence

- `groups`: actual Business binding retarget, invalid provider selector, independent
  healthy binding, scoped MariaDB publication failure across a complete scheduler
  cycle, recovery and removal. Manual grants and exact balances/postings remain
  unchanged. This supplements the existing offline staff/role/archive case.
- `realty`: supplied real Realty and Vault JARs with an isolated Realty schema;
  real registration, permission denial, failed debit and successful purchase;
  WorldGuard ownership, Treasury settlement, and scheduled Realty title-holder
  publication. Registration preserves existing WG ownership, so the fixture creates
  that ownership explicitly before registering. No mock economy provider is used.
- `nexo`: native custom-item purchase followed by selling; ordinary base-material
  rejection, failed-payment inventory restoration and successful retry, exact native
  versus ordinary inventory counts, balances and paired transaction postings.
- `rest-restart`: real process shutdown/start, persistent rejection of a superseded
  token, replay of the original committed transaction without another debit, then
  a distinct successful payment.
- `crash`: SIGKILL after an explicit world save and committed trade, followed by
  reconnect, unchanged ledger/inventory/shop identity and another settled trade.
  This is durable-checkpoint recovery, not an in-flight atomicity guarantee.
- `BalanceAccessTest`: all three aliases, exact funded offline-account output,
  a real world-context LuckPerms denial/restoration and self-node revocation, with
  unchanged balances, postings and transaction checkpoint.
- `explorer`: real game payment, business deposit, business shop sale and fine feed
  the same database used by Chromium. Tests verify private history, business account
  and activity data, public market price/volume, taxation totals, scheduled Business
  grants, retarget/removal revocation in the unchanged session, and manual-source
  independence. Lease expiry is modeled by moving its stored timestamp, not by
  waiting an hour. Authentication uses signed test sessions, not Keycloak login.

Acceptance now records a SHA-256 of the commit, tracked diff and untracked source
contents, rejects source changes during/between runs, and reads the Java version
from JAVA_HOME. This prevents a dirty-tree run from being described only by HEAD.

## Real Minecraft-realm login and proprietorship transfer

The user authorized use of the real `minecraft` realm. The new
`explorer-keycloak` profile uses its existing public `treasury-explorer` client
and already permitted `http://localhost:5173/api/auth/callback/keycloak` callback.
Two temporary, unprivileged realm identities carry Minecraft UUID attributes
matching the disposable offline players `WebAuthOld502` and `WebAuthNew502`.
The browser submits the real login form and Auth.js completes OIDC code exchange;
no signed-session injection is used in this profile.

This uncovered a production identity bug. Auth.js 5.0.0-beta.31 creates a random
local user ID even without an adapter and uses it for the default JWT subject.
Explorer exposed that ID as `keycloakSub`, so a fresh login could use a different
identity-link key. The JWT callback now explicitly copies the verified
`account.providerAccountId` into `token.sub` at sign-in. Existing sessions retain
their old subject until a fresh login; no remote sessions or existing identity
rows were rewritten. A focused unit regression checks the stable subject,
preservation on subsequent requests, and omission of access/refresh tokens.

The live browser test asserts both returned Keycloak subjects, both Minecraft
UUID claims and the resulting `explorer_identity` links with `linked_by=token-claim`.
It checks proprietor access and non-proprietor denial, then reconnects the real
players and runs `business transfer begin`, `confirm`, and `complete`. The same
browser sessions must show old-proprietor denial and new-proprietor access, while
the firm balance and posting count remain unchanged. GriefPrevention's existing
60-second reconnect cooldown is respected before connecting; failed logins are
not retried. Browser retries remain zero. Browser traces are disabled for this
profile to avoid recording passwords and OIDC exchanges.
